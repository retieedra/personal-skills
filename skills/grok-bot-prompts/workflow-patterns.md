# Conditional workflow patterns

These patterns capture the user's examples. Apply only the parts relevant to the requested bot.

## Post-call email and project updates

Learn from the owner's sent follow-ups. Link each example to its company, call, and deal or implementation stage at the time of sending. Historical stage requires historical evidence; today's CRM stage is not a substitute. Record review coverage. Separate the owner's writing from quoted replies, signatures, and automated content when learning voice.md.

Use completed calendar calls or Calendly events as triggers when requested. Match external attendees to companies and deduplicate the same meeting across sources. An external attendee makes a meeting a candidate, not proof that it needs a sales follow-up. Check for an existing follow-up before drafting.

Use the call transcript as the main source for discussion, decisions, and commitments; company records and prior email threads provide context. Granola is the preferred transcript source in the user's examples. An Attio transcript or notes can be a fallback when requested, with notes labeled as notes. Wait or surface the gap when the evidence is insufficient.

For voice.md, describe observed openings, tone, length, structure, recaps, requests, and closings, with representative evidence. Describe stage-specific differences only where supported. Product-specific Calendly links must be mapped from actual source context. Reti's example has two links for different products; this does not establish two links for every other bot.

For Linear or Attio changes, inspect existing issues and records before proposing new ones. Reuse an existing issue when it already covers the action. Separate commitments, suggestions, and unresolved questions. Keep owners and deadlines unknown unless supported. Show proposed changes with their sources, and obtain approval where the user requires it.

The review DM should contain the email draft, a link to its saved draft, proposed project/CRM changes where applicable, and material uncertainty. Track approval against the relevant version and action; report partial execution clearly so retries do not resend or recreate completed work.

## Account research and prioritization

Start from the actual CRM account list and existing tier definitions. Define the research question and evidence standards before the batch run. A representative pilot can establish the method; use a pilot size supplied by the user or label a chosen size as a proposal.

For CDI staffing research, classify evidence as in-house, outsourced, hybrid, or unknown. Verify current employment and distinguish the health system from individual facilities and vendors. Expired postings do not establish current staffing; active postings indicate hiring intent. A vendor relationship alone does not establish full outsourcing. Missing search results mean unknown, not outsourced.

Report observed staff counts as lower bounds, with source links, dates checked, confidence, and coverage limits. Keep fit recommendations separate from existing CRM tiers. Use available authorized sources; if access fails, report the limitation and continue with other sources without bypassing access controls.

Research output should include the account and CRM link, current tier, supported findings, uncertainty, and the recommended next step. Apply CRM changes or contact prospects only within the user's specified authorization. Keep batch progress so the work can resume without redoing completed accounts.
